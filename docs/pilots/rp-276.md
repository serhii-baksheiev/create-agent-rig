Status: run completed 2026-10-04 (UTC). The full criterion-by-criterion record
is [`rp-276-evidence.md`](rp-276-evidence.md); this page is the summary.

## Setup

- Fixture: the private repository `serhii-baksheiev/rig-1-2-parallel-pilot`,
  a small TypeScript package with a GitHub Issues queue, a five-task Spec Kit
  plan (T001 root; T002, T003 and T005 ready once T001 lands; T004 joins T002
  and T003), Vitest, CI and Definition-of-Done checks.
- An earlier run on 2026-10-01 landed T001 (#1, PR #7) and stalled the rest on
  the portable TDD verify-ship gate, which RP-398 later removed from the 1.2.0
  release contract. That run is history, not acceptance.
- Before this run the fixture's rig was upgraded to create-agent-rig master
  `1b261be` through the normal `upgrade` path (fixture PR #10), and the stale
  claims on #2 and #3 were released with comments.
- Controllers: three independent top-level Claude Code sessions (`claude -p`,
  unattended, the `loop` skill), pilot-A, pilot-B and pilot-C, each in its own
  clone. A Codex controller was attempted first for pilot-C and could not run
  (model unsupported for the account, then the account usage limit); the owner
  ruled that Codex is not used in this pilot and that three Claude Code
  controllers satisfy it, because the harness makes no essential difference to
  what the pilot proves. Cross-harness behaviour is not claimed here.

Every acceptance criterion listed in RP-276 was met in this run; the evidence
page cites the journal entries, timestamps and SHAs for each. The scenario's
root step is the exception: T001 had already landed in the 2026-10-01 run
(#1, PR #7), so this run began with the root done and exercised the parallel
tasks and the join, not the root unlocking them.

- No duplicate ownership: pilot-B's claim of #3, 28 s after pilot-A labelled
  it, was refused by the adapter (`claim-stale`) and pilot-B took #4 instead.
- Blocked work was never selected early: #5 was taken 35 s after #4 closed;
  before that, seven `nothing-selectable` stops each counted one item held by
  `blocked`.
- Only ready, in-scope, unclaimed work was returned; the controllers' own
  triage proposals were reported as out of scope, never selected.
- Width limited concurrency: three items ran in parallel; pilot-C and pilot-A
  ended on `nothing-selectable` while the join was blocked, and pilot-B alone
  drained the tail to `queue-empty`.
- Merge and close unlocked downstream work. Every close was made by the
  adapter after `BEFORE_CLOSE`, and every PR body used `Refs #n` rather than a
  closing keyword, which is the close order RP-330 needs.
- The existing pipeline was reused: RED before GREEN through `check-run`,
  reviewer fan-out and `pr-ship`, exact-head CI before each merge.
- Revalidation held on real drift (the master move from #11, the controllers'
  own comments) and each hold was re-read and answered before continuing.
- No manual assignment: no assignee was ever set. The operator's only actions
  after start were the contract amendment (#11) with the two escalation
  answers it settled, restarting headless sessions, and adding the bounded-wait
  instruction to the controllers' prompt.
- Run evidence: six run directories with decision and event journals, claim
  records, gate-round counters and check logs.

## What the run found

- The fixture's own contract still required RED/GREEN in the portable claim,
  which only the removed recorder could write. `code-reviewer` caught the
  conflict on #3 and #4, both controllers escalated instead of fabricating the
  field, and the operator amended the contract (#11).
- A headless `claude -p` session ends when the model finishes a turn, so two
  controllers stopped while waiting for CI and were restarted; an instruction
  to wait with a bounded foreground command fixed it for the rest of the run.
- The controllers filed three concrete skill-wording proposals in the fixture
  (#12, #16, #18). They and the headless-wait finding are carried to RP-409
  (1.2.1) rather than changed here.
