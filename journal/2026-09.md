### BEFORE_PR got a second explicit mode because 0.7.0 shipped a rulebook that contradicted itself, and the gate found two real bypasses in the fix before it found none

**Why this entry and not a decision record.** The rationale below is the kind
`docs/decisions/` exists for, and that is where it would normally go. It is
here instead because those records live under
`templates/agent-os/universal/docs/decisions/` and **ship into every generated
rig** — `npm pack` counts ten of them inside the tarball. Adding one would put a
new file into a rig that published 0.7.0 does not have, and this project's own
numbering rule made 0.7.0 a _minor_ for exactly that reason ("Five files land in
a generated rig that the published 0.6.2 does not contain… Shipping that as a
patch is the case the rule exists to prevent"). 0.7.1 is a narrow compatibility
patch, so the record goes in the journal, which is this repository's own and not
published. If the rationale later earns a record, the release that adds it is
the release that can afford a new file.

🔴 **Do not prune this entry.** `journal/README.md` says of these files "prune
freely: this is operational memory, not an archive", and that licence is why
calling the journal a _durable_ home would be a claim it does not support. This
entry is the only place the rationale is written down; if it is pruned before a
release can afford a `docs/decisions/` record, the reasoning is gone.

- **the defect, and it was found downstream rather than here.** AIC upgraded to
  the published `create-agent-rig@0.7.0` (npm `gitHead` `6589db36`) and could not
  run the gate at all. `pr-ship` step 4 names owner-directed work and hotfixes
  with no queue item as a legitimate path and tells the fan-out to declare it;
  step 1 then called `revalidate.mjs` with an unconditional `--ticket`, and the
  script refused without one. The lane was recognised everywhere — even
  `detect-missed-gate.mjs` already classifies a PR with no queue reference as
  `lane: 'owner-directed'` — except in the one place it had to execute.

- **why a second explicit mode rather than making `--ticket` optional.** An
  optional flag makes the mode a consequence of _absence_, and absence is
  indistinguishable from a caller who simply forgot. A run that omitted its
  ticket by mistake would silently get the weaker checkpoint and never be told.
  So both modes are named at the call site and passing neither is exit 1 — a
  mode chosen by absence is a mode nobody reviewed.

- **why "there is no item" cannot be proved, and is not claimed to be.** No
  check can establish that a piece of work has no tracker item; the tracker
  cannot be asked about an item that was never filed. What the command can
  establish is narrower and is exactly what it enforces: _this run declares no
  take-up, and this branch writes no claim_. The rest is the caller's word, and
  it is recorded as such — `ticket: null`, no invented id.

- **what the mode keeps, which is nearly everything.** It drops the claim
  comparison, because work with no item has no claim to compare, and drops
  nothing else. The `main:<path>` drift check against the default branch —
  including the paths a `check-premises` record cited — is the same code the
  ticketed path runs, and holds on the same exit 2.

- **four refusals, and one of them is why the mode is not a bypass.** Exit 1,
  nothing journalled: an unresolved `revalidationHold`; a take-up this run
  declares; any touch of a tracked `.rig/claims/*.json` — added, modified,
  removed or renamed; and `BEFORE_CLOSE`. Run state is read fail-closed, so an
  unreadable `state.json` refuses rather than reading as an empty run.

- 🔴 **the gate earned its keep, twice.** Three rounds, blockers 8 → 2 → 0.
  Round 1: `security-scanner` _measured_ a bypass — a ticketed BEFORE_PR that
  exited 2 `UNVERIFIABLE` latched a hold, and re-running the same checkpoint as
  `--owner-directed` exited 0 with nothing in the repository changed. The first
  implementation read `takeUps` and never `revalidationHold`, and neither other
  refusal could fire in that state _structurally_: `takeUps` is never populated
  at all on `plan-md`, the default adapter in every generated rig, and the
  commonest hold is a _missing_ claim record — precisely when the branch writes
  none. The property was asserted in three documents and enforced nowhere.
  Round 2: the fix for a _prose_ contradiction opened a second route to the same
  bypass, and the test written for it was indistinguishable from `true` under
  mutation. Both were found by cold readers, neither by the session that wrote
  the code. That is the whole argument for review-context isolation, measured.

- **known limits, stated because a governance mode is trusted as far as it is
  described.** With no `RIG_RUN_DIR` there is no run state, so the hold and
  take-up refusals cannot fire — the command says so on stdout and in
  `evidence.runState` rather than reporting a clean check. The claim refusal
  reads the branch diff, so a record already on the default branch, or
  uncommitted, is not seen. And `--base` decides more here than the verdict: the
  claim-touch refusal reads the same range, so `--base HEAD` disarms it too.

- **the HOLD asymmetry, and why it is deferred rather than hidden.** A ticketed
  HOLD has two stops: exit 2, and a durable `revalidationHold` latch **the next
  selection reads**. Only selection — the close path stops on `BEFORE_CLOSE`'s
  own exit 2 and never reads the latch, so "selection and closure both read it"
  would overstate the baseline this asymmetry is measured against.
  An owner-directed HOLD has **only exit 2**. An outcome can be recorded for it,
  addressing the detection by mode rather than by key, but no second durable
  stop exists yet — so a caller that ignores the exit code is not stopped again
  by this mechanism. `recordRevalidationHold` requires a string ticket, and giving
  it one would mean inventing the identifier this whole mode refuses to invent;
  widening it is a run-state schema change, which is Tier 2 in its own right.
  Filed as **RP-96** (ticketless, mode-addressable durable latch), deliberately
  not folded into this patch: 0.7.1 exists to unblock a downstream integration
  of an already-published release, and landing a schema change beside it would
  make a narrow compatibility fix into something a reviewer has to re-scope.
  `security-scanner` examined the asymmetry explicitly and judged it shippable —
  the latch exists to stop the _next selection_ building on unresolved drift,
  and the take-up refusal guarantees such a run holds no item for a later
  selection to build on.

- **the Windows lane, classified rather than retried.** `windows-unit` went red
  on the PR head with one annotation — a 15 s timeout in `codex.test.ts`, a file
  this branch does not touch — and zero AssertionErrors. Evidence, not

  release blockers.

- **what is still true when this entry is written.** 0.7.1 is _prepared_, not
  published: both manifests read 0.7.1, `templates/release-ledger.json` carries
